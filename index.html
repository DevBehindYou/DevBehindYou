Why I build

Most apps ask for too much.

Too many apps want an account, a subscription and your data before they do anything useful. I build the opposite: tools that work offline first, keep your data where you put it, and explain in plain words what they do with it.

Atomic Notes started three years ago as a small notes app. I shelved it, came back, and rebuilt it from scratch with sync to your own Google Drive and an end-to-end vault. MDify came from a $50 API bill that showed how much raw PDFs cost in AI chats. The best projects on this page started as a problem I had myself.

I publish the code because building in public keeps me honest. A README that says “not verified on a device yet” is more useful than a landing page that says “production-ready”.

How I work

Plan it, build it, test it, write it down.

Every project follows the same four steps and the same release checklist. That is why the progress cards below can show real numbers.

  1. 01

    Plan

    A short spec, a data model and the screens before any code. The docs folder comes first.

  2. 02

    Build

    Small commits in phases. Each phase ends with something that runs.

  3. 03

    Test

    Unit and integration tests in CI, then a security review and a check on a real device.

  4. 04

    Ship and record

    A tagged release, a changelog, and a README status section that says what’s verified and what isn’t.

Release checklist

What a build needs before I call it done.

The list I check before tagging a release. When an item is still open, the README says so.

  • Tests pass in GitHub Actions
  • No secrets in the repo, keys in the environment or the Keystore
  • Works offline, or fails with a clear message
  • Keyboard, screen reader and contrast checks
  • Lighthouse and Core Web Vitals checked on the web
  • Signed release or a live deploy
  • README with setup steps, status and roadmap
  • A license file that matches what the README says
